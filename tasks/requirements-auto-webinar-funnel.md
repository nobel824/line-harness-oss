## 3. 仕様書に足すべき前提（P-1〜P-5）

### P-1【解消済み】cron が止まると導線が丸ごと沈黙する

本導線の時限処理は**すべて毎分 cron 依存**である（30分後のウェビナー案内 / picker離脱 / no-show /
フォーム後未予約 30分・24時間 / 前日・1時間前リマインド）。

2026-08-16 22:00 JST から **Workers Free プランの CPU 上限 10ms により毎分 cron が `exceededCpu` で全滅**し、
8/17 の予約配信が `sending` のまま固着した実績がある。fetch はバースト許容で生き残るため
**「管理画面は動くのに配信だけ死ぬ」**という形になり、エラーも出ずに気づけない。

- 対処は **Workers Paid（$5/月）で上限30秒**にすること。コード側で 10ms 未満に削る道は現実的でない（健全時でも P50 約12ms）
- **本導線は cron 処理を6種類増やすため、Free のままでは確実に再発する**
- → **2026-08-27 にユーザー確認済み: Workers は Paid**。CPU 上限30秒のため本前提は解消した
- ただし本導線は cron 処理を6種類増やすため、**リリース後に `wrangler tail` で `event.cron` の `outcome` を1度確認する**（T-D）

### P-2 LINE 配信通数がファネルの処理人数を決める

プランは**ライト（月5,000通）**、今月すでに **2,989通** 消費済み（残 約2,000通）`[実測]`。

特典の即時返信は reply API で**課金対象外** `[公式]`。それ以外はすべて push。

**「最大8通/人」で見積もってはいけない。** 追客の各ステージは**互いに排他的な分岐**（ピッカーで離脱した人は
no-show にならない）であり、全部を踏む人は存在しない。一方で当初の見積りからは
**開始5分前の入場リンク push**（`webinar-reminders.ts:136`。予約1件ごと、再予約でも再送）が漏れていた。

正しい見積り方は「段 × その段に到達する人数 × 通数」の期待値である。段別転換率は未計測なので、
**リリース後に実測して埋める**。現時点で確実に言えるのは次の2点:

- 唯一**流入者全員**に飛ぶのは F-3 のウェビナー案内であり、ここが通数の**支配項**である
- → F-3 は特典 reply への同梱（0通）＋ 未クリック者のみ翌日 push に設計変更した（後述）。
  これによりトップオブファネルの通数はクリック率の分だけ削減される
- 今月の残枠は約2,000通 `[実測]`。段別転換率が出るまでは**残枠を配信の上限として運用する**

### P-3 動画は HLS 変換が必要

提供された素材は `2026-08-27 16.54.00 達貴 奥田のZoomミーティング/video1125579345.mp4`
（**3,449秒＝57分29秒** / 1920x1080 / h264+aac / 89MB）。

- 現在のウェビナー設定 `durationSeconds` は **3600（60分）で実尺と151秒ズレている** → 3449 に修正が必要
- CTA 表示 `showAtSeconds` は現在 2700（45分＝実尺の78%地点）。仕様書の狙い（終盤80〜87%）に合わせるなら **2,760〜3,000秒**が範囲
- ffmpeg で HLS 化し、R2 `line-harness-images` バケットへアップロードしたうえで `videoPrefix` を設定する作業が必要

### P-4 LINE 公式アカウントガイドラインの型に当たらないか

vault の調査結果では、禁止されているのは事業類型ではなく**訴求文言と誘導構造**であり、
〈「儲かる」または「◯◯するだけ」の謳い文句〉＋〈メルマガ登録・動画販売・セミナー誘導〉が条文の型である `[公式]`。

仕様書の例文「**3ヶ月でXフォロワー1万人を達成するまでにやったこと**」＋ウェビナー誘導は、
**この型に接近している**。25万人規模の事業者が同型を運用している例が逐語的に条文へ抵触していることも確認されており、
**「大手もやっている」は安全の根拠にならない**。

- アカウント停止＝**友だち1,002人の全損**で、復旧手段が無い
- → 文面確定時に条文当てを行う。数値実績を出す場合は「誰でも再現できる」と読める表現を避ける
- 法的な可否判断は本書の範囲外（論点の指摘まで）

## 5. 機能要件と受け入れ条件

Acceptance Criteria は「主語・動詞・期待結果」で記述する。検証手段のない要件は置かない。

### F-1 ウェビナー編集画面から追客・予約設定ができる

`webinar_followup_configs` を読み書きする REST API は**存在しない**ことを確認済み（`SELECT` 利用のみで INSERT/UPDATE のルートが無い）。
現状の設定手段は D1 への直接 SQL（`docs/wiki/28-Google-Calendar-and-Webinar-Booking.md:91-104` に例）。
したがって本要件では **API の新規追加と UI の追加をセットで行う**。

`webinar_followup_configs` の以下9項目を管理画面から設定可能にする。
`is_active` / `booking_menu_id` / `booking_url` / `first_delay_minutes` / `second_delay_minutes` /
`picker_delay_minutes` / `no_show_delay_minutes` / `booking_delay_minutes` / `booking_second_delay_minutes`

**AC-1-1**: 運用者がウェビナー編集画面で予約メニューを選択して保存すると、`webinar_followup_configs.booking_menu_id` に
その ID が永続化される（保存後に画面を再読み込みしても選択が保持される）。
**AC-1-2**: 運用者が各追客の遅延分数を変更して保存すると、対応するカラムが更新される。
**AC-1-3**: 運用者が D1 を直接操作することなく、上記9項目すべてを設定できる。
**AC-1-4**: 予約メニューの選択肢は `/api/booking/admin/menus` の実データから生成される（ハードコードしない）。
**AC-1-5**: 保存経路が型キャストで握り潰されていないことを、保存 → API 再取得の実データ照合で確認する。

> 補足: 過去に SegmentBuilder が `segment_conditions` をキャストで投げ、PUT も update も受け取らず
> **サイレント破棄**していた事故がある。「保存できたように見える」で判定しないこと。

### F-2 特典キーワード受信で導線が起動する

**対象キーワードは `特典`（完全一致）1本に確定**（2026-08-27 ユーザー決定）。
他15本の特典キーワード（`スキル` `プロンプト` `クロード` `コワーク` `Codex` `GPT` ほか）は**今回の導線に載せない**。
それらの受け取り者はウェビナー案内を受け取らないため、必要になった時点で同じ automation を複製して追加する。

**AC-2-1**: 友だちが対象キーワードを送信すると、特典本文が**reply API**で即時返信される（既存 auto_replies を維持し、課金枠を消費しない）。
**AC-2-2**: 同じ受信で `特典請求` タグが付与される。
**AC-2-3**: 同じ受信でウェビナー案内シナリオに登録される。
**AC-2-4**: `特典` 以外のメッセージ（`特典です` のような部分一致を含む）では、タグが付与されない（`keyword_exact` の完全一致が効いていることを実データで確認）。
**AC-2-5**: 同一受信で特典本文が**二重送信されない**。検証は、`特典` 送信後に該当 friend の会話ログ（`GET /api/chats/:friendId`）で outgoing が1件だけであることを確認する。

> 実装方針: automation のアクションは `add_tag` と `start_scenario` のみとし、
> 本文送信は既存 auto_replies に任せる。既存の「先行利用リード自動タグ」が同じ構成で、
> タグ保持者17人全員が実際に当該キーワードを送信していること（誤爆ゼロ）を実データで確認済み。
> automation の `send_message` は常時 push ではなく、**replyToken があれば reply、無ければ push にフォールバックする**
> （`event-bus.ts:298-316`）。本文送信を automation に持たせないのは課金理由ではなく、**二重送信を防ぐため**である。
>
> あわせて `keyword_exact` に**空文字を入れてはならない**。JS の falsy 判定でスキップされ、
> 他に条件が無ければ `return true`＝**全メッセージに無条件マッチ**する（`event-bus.ts:214`）。

### F-3 ウェビナー案内が届く（特典同梱＋翌日フォロー）

**2026-08-27 ユーザー決定により、仕様書の「30分後 push」から設計変更した。**
特典の即時返信は reply API で課金対象外のため、**ウェビナー案内をこの返信に同梱**すればトップオブファネルの
通数が 0 通になる。そのうえで**リンクを踏まなかった人にだけ翌日 push** でフォローする。

**AC-3-1**: 友だちが `特典` を送ると、特典本文と同じ返信の中にウェビナーへのリンクが含まれている（追加の push が発生しない）。
**AC-3-2**: そのリンクは事前に作成した `tracked_links` の `/t/<shortCode>` であり、クリックすると「ウェビナー案内クリック」タグが付与される。
**AC-3-3**: 特典請求から翌日、**リンクを踏んでいない友だちにだけ**ウェビナー案内が1通 push される。
**AC-3-4**: リンクを踏んだ友だちには翌日 push が届かない（シナリオの `tag_exists` 分岐で除外されていること）。
**AC-3-5**: 一度の特典請求で届く LINE の吹き出しが3つ以内である（LINE の1配信あたりの上限） `[公式]`。

> **生URLを本文に書いてはならない。** 配信のたびに `name: "auto: <url>"` の tracked_link が新規生成され、
> `tag_id` も `scenario_id` も NULL になるためクリックしてもタグが付かず、クリック数も分散する。
> 2026-08-04 のクラファン7日ステップで7通すべてがこの状態になり、クリック起点の自動化が一度も発火しなかった実績がある。

### F-4 ウェビナー視聴からCTA・フォーム・予約まで繋がる

**採用経路を「ウェビナー個別相談」に固定する**（D-6 の a）。Meet の自動生成と、
フォーム送信後に同一画面で空き枠を出す実装（`apps/worker/src/client/webinar/main.tsx:1246-1258`）が
この経路にしか無いため。一般予約経路を使うと Meet が付かず、リマインドも2時間前になる。


**AC-4-1**: 友だちがウェビナーを視聴し、実尺の所定地点に達すると CTA が表示される。
**AC-4-2**: CTA をクリックすると無料相談フォームが表示される。
**AC-4-3**: フォーム送信後、**外部サイトに遷移せず**空き日時が表示される。
**AC-4-4**: 日時を選択して確定すると、Google Calendar に予定が作成され、Google Meet URL が生成され、LINE に予約確定通知が届く。
**AC-4-5**: Google Calendar / Meet の作成に失敗した場合、予約が `cancelled` になり 503 が返る（＝「予約だけ成功して Meet 無し」を残さない）。
この挙動はウェビナー個別相談経路の既存実装（`webinar-consultation-booking.ts:390-403`）であり、**変更しない**。

### F-5 離脱追客が設定どおり発火する

**AC-5-1**: セッションピッカーを開いたが予約しなかった友だちに、`picker_delay_minutes` 後に追客が届く。
**AC-5-2**: 予約したが参加しなかった友だちに、`no_show_delay_minutes` 後に次枠案内が届く。
**AC-5-3**: フォーム送信後に相談を予約しなかった友だちに、`booking_delay_minutes` 後と `booking_second_delay_minutes` 後の計2回届く。
**AC-5-4**: 各追客は friend×webinar×kind で一意であり、重複送信されない（UNIQUE 制約が効いている）。
**AC-5-5**: CTA をクリックしたがフォームを送信しなかった友だちに、`first_delay_minutes` 後と `second_delay_minutes` 後の計2回届く（**第4のステージ**。`webinar-followups.ts:112-141`）。
**AC-5-6**: そのために CTA が `webinar_ctas` に `form_id` を持つ形で設定されている（外部URLのままだと抽出条件を満たさず、このステージが永久に発火しない）。
**AC-5-7**: 追客6通すべての本文が、実尺（57分29秒）・実際の相談枠（30分）・実際のフォーム名と矛盾しない。「21分」「AI導入診断」「15分枠」が残っていない。
**AC-5-8**: `is_active` を 0 から 1 に戻したとき、サーバー側で `stage_enabled_at` が現在時刻に打ち直され、**有効化以前に蓄積した離脱者に一斉送信されない**。

> **バースト送信の防壁**: 候補抽出SQLは全ステージで
> `datetime(source) >= datetime(COALESCE(cfg.stage_enabled_at, cfg.enabled_at))` を門にしている
> （`webinar-followups.ts:201,230,253,259,290`）。これが「有効化以前の過去リードに一斉送信しない」唯一の防壁であり、
> UI から ON/OFF できるようにする際に打ち直しを忘れると、毎分50件ずつ push が流れて残枠を黙って食う。
>
> **相関バリデーション**: `submitted_no_booking_*` は `booking_menu_id IS NOT NULL AND booking_url IS NOT NULL` の
> **両方**を要求する（同 `:299`）。UI で2フィールドを別々に露出し片方だけ保存されると、そのステージだけ沈黙する。

### F-6 リマインドが2回届く

**AC-6-1**: 予約確定後、**前日**と**開始1時間前**の2回、LINE リマインドが自動登録され送信される
（`meet-consultation-reminders.ts:73-84` の `day_before` / `hour_before`）。
**AC-6-2**: 送信は **push** であり（`meet-consultation-reminders.ts:273`）、通数見積り（P-2）に算入されている。

> 一般予約経路を選ぶと2通目は**既定2時間前**になる（`booking-types.ts:101-103`）。1時間前が要件なら F-4 の経路固定を守ること。

### F-7 ウェビナー動画が再生できる

**AC-7-1**: 提供された mp4 を HLS 変換して R2 にアップロードし、`videoPrefix` を設定すると、視聴画面で動画が再生される。
**AC-7-2**: `durationSeconds` が実尺 3449 と一致している。
**AC-7-3**: `showAtSeconds` が終盤（実尺の80〜87%＝2,760〜3,000秒）に設定されている。
**AC-7-4**: ウェビナーの `status` が `draft` から公開状態に変更されている。
**AC-7-5**: `slug` が `test` から実運用向けの値に変更されており、視聴URLに `test` が含まれない。

### F-8 分析でファネルが追える

この導線は7つ以上の接ぎ目を持ち、その各段が「候補SQLが0行を返す」という**エラーの出ない形**で死ぬ。
E2E テストが保証するのはリリース日の健全性だけで、3週目に静かに止まったことは教えてくれない。
したがって**段別カウントは Phase 1 の必須項目**とする（当初「拡張する場合」としていたのを昇格）。

**AC-8-1**: 既存の Analytics で 予約 / 参加 / 90%以上視聴 / CTAクリック / フォーム送信 が確認できる。
**AC-8-2**: `webinar_picker_opens` / `webinar_registrations` / `webinar_viewers` / `form_submissions` /
`webinar_journey_followups`（kind別・status別）の件数が1画面で確認できる。
**AC-8-3**: `status='failed'` の追客件数が表示される（現在は記録されるだけで誰の目にも触れない。`webinar-followups.ts:433-436`）。
**AC-8-4**: いずれかの段が 0 件のまま滞留していることが、その画面を見れば分かる。
