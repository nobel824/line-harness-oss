## ① 結論

**1,008人へのウェビナー一斉案内は今週やらない。** 次の3手をこの順で実行する。

1. **下流の修理を先に終わらせる**（`booking_url` 投入で `submitted_no_booking_*` を解禁 /
   相談枠ディープリンク `page=consult` / CTA到達の再設計）。所要2〜3日
2. **「熱源」約30人に、一斉配信ではなく LINEチャット（1:1）で当てる。通数0通。**
   ウェビナーを必須にせず**無料相談へ直行**させる。目的は売上ではなく
   **商談プロセスを初めて1回貫通させること**
3. 下流の貫通を確認してから、**残りを2波（直近反応層 → 休眠層）に分けて投入**。
   一斉配信は各層1通ずつ、合計1周まで。**全員に2通は通数予算上そもそも不可能**

既存リストに対しては **ウェビナーを「必ず通す関門」から「任意の補助教材」へ降格**する。主導線は無料相談直行。

## ② その理由

1. **1,008人は「伴走1〜2件分の在庫」**。標準シナリオで相談実施6件・成約2件・うち伴走1件。
   桁を勘違いすると雑に使う
2. **壊れたパイプに補充のきかない水を流すことになる**。相談0の原因は
   (a) CTA未到達 (b) フォーム送信後に枠へ戻る導線が構造的に無かった（PR #63 で8/28に半分修理・
   `booking_url` は今も未設定）(c) 需要不足 — の3つが分離できない。
   流すと**一度きりの新規性**（「新しいウェビナーを公開しました」は二度使えない）を消費する
3. **「送らない」も有料**。頻度を下げると解約は減るが短期売上も5〜8%落ちる
   （Baek et al. `[実証]` / `2026-0803-frequency-trades-churn-against-revenue`）。
   ただし**2〜3日の修理待ちのコストはほぼゼロ**
4. **既存リストのボトルネックは教育不足ではなく手続き**。返信13名 → フォーム回答3名で
   **77%が手を挙げた後に死んでいる**（`2026-0802-warm-leads-die-at-the-form` `[実測]`）。
   57分の視聴を課すのは急所に摩擦を重ねる設計
5. **熱源30人には通数もブロックコストもかからない**。1:1チャットは課金対象外 `[公式]` で、
   一斉配信より1回あたりの離脱コストが構造的に低い（`2026-0731-line-broadcast-costs-list-attrition`）

## ③ やらない方がいいこと

| やらない | 理由 |
|---|---|
| 1,008人に一斉配信で「無料ウェビナー公開しました」 | 下流未修理／新規性を1回で使い切る／通数の半分を1発で消費 |
| **主見出しに「3ヶ月で1万フォロワー」＋セミナー誘導** | 〈成果の謳い文句〉＋〈セミナー誘導〉は情報商材・能力開発商材の**条文の型そのもの**（`2026-0803-guideline-bans-the-pitch-not-the-business` `[公式]`）。**停止＝1,008人全損で復旧手段なし**。大手が同型を運用していることは安全の根拠にならない |
| 既存リスト向けに別ウェビナーを新規制作 | 既存1本の下流が未検証。ローンチは**増幅装置であって需要を作らない**（`launch/04-types.md` `[観察]`） |
| 既存リストに新しい特典を挟む | 全員分の通数がかかる上に〈特典 → ウェビナー → 相談〉が揃って規約の型に寄る。**分割も日をずらすのも回避策にならない** |
| 「今だけ」「あと◯席」 | アーカイブが3日間実在する以上、有利誤認（`launch/_disputes.md` §1 `[法規]`）。8/28に本人が既に却下済み |
| 教育ステップ3〜5通を全員に流す | 残枠2,000通に対し 1,008×3＝3,024通で**物理的に不可能** |
| ウェビナー予約数を成果として報告 | 予約7件で相談0件が現に起きている。予約は**中間在庫** |
| LINE公式のA/Bテスト機能で検証 | ターゲットリーチ5,000人以上が要件で**1,008人では使えない**（`2026-0803-ab-test-needs-5000-reach`） |

## ④ 推奨ファネル

```
既存リスト 1,008人（≒到達可能 790人 ※ブロック率未計測）
│
├─[S1] 熱源 約30人 ────── LINEチャット 1:1（通数0）
│      過去に返信/フォーム/予約/視聴/相談        │
│                                    ┌──────┴──────┐
│                            無料相談へ直行     「先に見たいなら」
│                            （主導線）        ウェビナー（任意）
│                                    └──────┬──────┘
│                                           ▼
├─[S2] 直近90日反応 約200人 ── 一斉配信1通 ─→ 選択式1タップ
│                                  │  ├ A「相談枠を見る」→ 相談
│                                  │  └ B「まず内容を見る」→ ウェビナー → CTA → 相談
│                                  └→ 無反応は追撃しない（次の波で扱う）
│
└─[S3] 休眠 約560人 ────── S2の結果がGOなら 一斉配信1通（同型）
                                        ▼
                            ┌───────────────────┐
                            │ 無料相談 実施（30分）│ ← 唯一のKPI原点
                            └─────────┬─────────┘
                                      ▼
                        X Studio / X支援プラン（フロント＝選別装置）
                                      ▼
                             上位伴走プラン（本体の売上）
```

**設計の核**: 送信側で温度を当てにいかず、**1通の中に2つの出口を置いて受信者に自己選別させる**。
セグメント管理の工数が消え、「ウェビナーを見た人しか相談できない」という不要な関門も消える。

## ⑤ セグメント

**制約**: 一斉配信のターゲットは `all | tag | multi-account-dedup` の3種のみ
（`packages/db/src/broadcasts.ts:2`）。**「最終反応日」で直接絞る機能は無い**ので
`chats.last_message_at`（`packages/db/migrations/002_round3.sql:174`）から抽出して
一括タグ付けする作業が1回必要。**タグは流入より先に付けないと後から絞れない**
（`2026-0803-tag-must-be-assigned-before-the-inflow`）— この教訓の請求書が今来ている。

| 優先 | セグメント | 想定 | 手段 | 通数 | 何を出すか |
|---|---|---|---|---|---|
| **1** | **S1 熱源**（返信13＋フォーム3＋予約7＋視聴3＋過去相談者・重複除く） | **〜30** | **LINEチャット 1:1（手作業）** | **0** | 相談直行。ウェビナーは任意 |
| 2 | S2 直近90日反応 | 〜200 | 一斉配信（tag） | 200 | 2出口の選択式1通 |
| 3 | S3 それ以外／休眠 | 〜560 | 一斉配信（tag） | 560 | 同型。文面のみ「ご無沙汰」文脈 |
| — | オプチャ重複層 | 〜900 | **追撃しない** | 0 | オプチャは観測、公式LINEは本命（`2026-0803-overlapping-lists-cannot-be-chased-twice`） |

**S1を分けるのが工数対効果で圧倒的**。30人の手作業は1〜2時間、通数0、最も成約に近い層に最も丁寧な接触。
**これ以上細かく切らない**（登録目的別のタグは過去に付いていないので遡って作れない）。

## ⑦ テスト設計

A/Bテスト機能は使えず（下限5,000）、n=100〜200では**相談申込のような低頻度イベントを統計的に判定できない**。
「A/Bテスト」ではなく**逐次投入＋停止規則**として設計する。

| 項目 | 設計 |
|---|---|
| 母数 | ① S1 30人（テストではなく本命）→ ② S2 前半100 → ③ S2 後半100 → ④ S3 560 |
| 比較するもの | **訴求ではなく「出口の数」**。②は2出口、③はウェビナー単独。**2つ以上の変数は回せない** |
| 観測期間 | 各波 **72時間**（統計は14日で打ち切り・直後24時間は約1%誤差の推定値 `[公式]`） |
| GO条件 | クリック率 ≥ **4%**（分母＝配信数）／ ブロック増 ≤ **1.5%**／ 相談申込 ≥ **1件** |
| STOP条件 | ブロック増 ≥ **3%**／ クリック率 < **2%**／ クリックはあるのに**相談申込0が2波連続** |
| 判定に使わない | ウェビナー予約数（予約が増えて相談0が現に起きている） |

## ⑧ KPI

**注意**: LINE の開封率は公式定義があるが**100%表示ベース／iOS・Androidのみ／14日で集計終了／
既読だけでは不算入**（`2026-0803-line-has-open-rate-but-defined-differently` `[公式]`）。
「開封率60%」「クリック率30%」は**一次出典に到達できない** `[伝聞]`。
**下表は相場値ではなく判断を分岐させるための閾値** `[自己導出]`。

| 指標 | 最低 | 合格 | かなり良い | 備考 |
|---|---|---|---|---|
| 開封率（配信数ベース） | 40% | 55% | 70% | 構造的に過小。**他社と比べない** |
| クリック率（**分母＝配信数**） | 2% | 4% | 8% | 分母を開封数にすると跳ねる。混ぜない |
| ウェビナー予約率（クリック者ベース） | 25% | 40% | 55% | 現行実測 **53.8%**（n=13）。**既に強い** |
| 視聴開始率（予約者ベース） | 35% | 55% | 75% | 現行実測 **42.9%**（n=7） |
| **CTA到達率**（視聴開始者のうち49:57まで残る率） | **20%** | **40%** | **60%** | **現行実測ほぼ0%。最大の穴** |
| 無料相談 申込率（クリック者ベース） | 8% | 15% | 25% | S1直行導線を含む |
| 無料相談 実施率（申込者ベース） | 60% | 80% | 90% | no-show込み |
| 商談成約率 | 15% | 30% | 45% | 「30%」はベンダー取材の**成功バイアス込み** `[観察]`。**自社実績0件＝目標でなく仮説** |

### 最重要KPI: 無料相談の「実施」件数（週次）

1. **現在ゼロだから。** ゼロの指標だけが施策の成否を白黒で答える
2. **売上に対して唯一、線形に効く。** 予約も視聴もCTAも実施件数を増やす手段でしかない
3. **成約プロセスが未検証だから。** 商談を1件もやらずに「オファーが悪いのか導線が悪いのか」は決まらない。
   **最初の3件は売上のためではなく診断のために取りに行く**

副次で**ブロック率の前後差**（リスト資産の減価償却費）。
**自社のブロック率は一度も測っていない**（vault の Open Thread に2026-08から残存）。S3の波が初計測。

## ⑨ 売上シミュレーション

**前提**: 到達可能 = 1,008 ×(1 − ブロック率22%) ≒ **790人**。
22%は業界ベンチの5,000人未満帯 `[実測]` で**自社の実測値ではない**（最大の未知数）。

| 段 | 弱気 | 標準 | 強気 |
|---|---|---|---|
| 到達 | 790 | 790 | 790 |
| 反応（クリック／1:1返信） | 24（3%） | 47（6%） | 79（10%） |
| ウェビナー予約 | 5 | 14 | 30 |
| 視聴開始 | 2 | 7 | 20 |
| **無料相談 申込** | **4** | **9** | **18** |
| **無料相談 実施** | **2** | **6** | **13** |
| 成約（実施の15/30/45%） | **0〜1** | **2** | **6** |

**単価は実価格に差し替えること**（vault に X Studio の確定価格が無いため仮置き。捏造しない）。
参照できるのは「バックは数十万円/月のサービス」のみ（`2026-0803-back-end-ltv-sets-allowable-cac`）。

| シナリオ | 成約 | 内訳 | 売上（伴走30万×3ヶ月／フロント1.5万×12ヶ月の仮置き） |
|---|---|---|---|
| 弱気 | 0〜1 | フロント1 | 0 〜 18万 |
| 標準 | 2 | 伴走1＋フロント1 | 90万＋18万 ≒ **108万** |
| 強気 | 6 | 伴走2＋フロント4 | 180万＋72万 ≒ **252万** |

**この表の読み方が本題**: 標準シナリオの売上108万のうち **83%が伴走1件**から来る。
フロントの売上は誤差。つまり成否は**「伴走1件が出るか」というほぼ二値の事象**で決まり、
それを決めるのは**相談を6件実施できるか**。そして6件は **S1の30人だけでも到達しうる**（30 × 20%）。
→ **1,008人を全部使わなくても標準シナリオは達成できる。** これが「全員に送る」を否定する
最も強い数量的根拠。790人を消費して得られる増分は主に**強気への上振れ分**で、
**下流が壊れている状態ではその上振れは発生しない。**

8. **push 残枠を実数確認**し S2+S3 の1周（約760通）が入るか検算。
   **429で落ちても Reply は動き続けるので気づけない**（`2026-0802-reply-doesnt-consume-push-quota`）
9. **配信直前のブロック数／ターゲットリーチを記録**（**自社ブロック率の初計測**）
10. **72時間後に段別カウント（分析タブ）で判定**し、GO なら S2 へ

## 批判的再検討

**Q1. 本当に売上最大化か。** 言い切れるのは、標準シナリオの売上の83%が伴走1件から来る構造。
必要なのは「相談実施6件」で、S1の30人だけで届きうる。言い切れないのは、
**成約率の仮説値がベンダー取材由来（成功バイアス込み）で自社実績が0件**であること。
だから最初の3件を「診断」と位置づけている。

**Q2. 予約率が目的化していないか。** 元案はしていた。実測は逆で、
**予約率53.8%・視聴開始42.9%は既に許容範囲。壊れているのは CTA到達（ほぼ0%）とその先**。
だから既存リストに対して**ウェビナーを主導線から外した**＝予約数を意図的に減らす設計であり、
予約率目的化の明示的な否定。

**Q3. 1,008という数字に引っ張られていないか。** 元案は引っ張られている。本案は
「伴走1〜2件分の在庫」に翻訳して解毒した。補強証拠: **登録者34人で売上99万円** /
**登録者10人前後で先行案内が3倍**（`2026-0803-small-lists-still-convert` `[観察]`）。
ただし逆方向（温存を美徳にして永久に送らない）も失敗なので、Phase 0 を2〜3日で切っている。

**Q4. 新規と既存を同じに扱っていないか。** 元案は同じ導線を適用しようとしていた。本案は分ける。

| | 新規リード | 既存リード |
|---|---|---|
| ボトルネック | **信頼の不足** → 教育（ウェビナー）が効く | **手続きの摩擦** → 実測77%がフォームで死ぬ |
| 主導線 | 特典 → ウェビナー → 相談 | **相談直行**。ウェビナーは任意 |
| 通数 | 応答メッセージ経由で**0通** | 一斉配信で**全員分課金** |
| 補充可能性 | **月40人ずつ補充される** | **補充されない。一度使うと戻らない** |

4つ目の非対称が決定的。**新規は失敗しても来月また来るが、既存1,008人は失敗したら終わり。**
だから新規で実験し、既存で回収する。

## 結論の修正（1点）

①は修正しない。ただし **今週タスク3（CTA到達の穴）を S2 配信の GO条件に昇格**させる。
CTA到達率がほぼ0%のまま S2 の200人を流すと、**ウェビナー経由の出口が実質存在しない状態で
配信する**ことになり、「2出口 vs 1出口」の比較がテストとして成立しない。

> **修正後のGO条件**: S1で相談実施 ≥1件 **かつ** CTA到達率 ≥20%
> （またはウェビナー画面に常時表示の相談リンクが稼働している）
