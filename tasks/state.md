→ **1 tick あたりの送信上限に変え、溢れた分は NULL のまま次 tick に回す。**
消化は「窓を過ぎた行」だけに限定する。cron は毎分発火なので実効の捌き能力は十分。

→ **教訓: 送信経路のガードは「何を止めるか」の範囲を必ず明示する。**

**設計アドバイザー（Fable 5）の結論と、PM が裏を取った事実:**

1. **記録はカラム追加**（`reminded_day_before_at` / `reminded_1h_at`）。`notified_at` は5分前用としてリネームせず残す。
   `UPDATE ... WHERE 列 IS NULL` → `changes > 0` の原子的クレーム（`webinars.ts:1161`）をそのまま3つ並べられる。
   別テーブル案は due クエリに kind ごとの `NOT EXISTS` が要り、Free プランの CPU 制約下で不利。次の migration は **078**。
2. **`X-Line-Retry-Key` が `reg.id` そのまま**（`webinar-reminders.ts:102`・**PM が実コードで裏取り済み**）。
   3通にすると **1時間前と5分前が同じキーで LINE 側に黙って dedupe され、後の1通が消える**。
   **キーは `${reg.id}:${kind}` に必ず分ける。これが最大の沈黙故障リスク。**
3. **窓は下限と上限の両方をSQLに持ち、`IS NULL` は重複排除専用に格下げする。**
   現行が安全なのは `IS NULL` ではなく「session 終了」という上限が入っているから（`webinars.ts:1151`）。
   `トリガー時刻 <= now AND 列 IS NULL` だけで書くと**過去セッションのNULL行が全件1 tickで一致＝バースト**。

   | kind | 窓 | 外したら |
   |---|---|---|
   | 前日20:00 | `[trigger, trigger+猶予2〜4h]` かつ `session_start_at > now` | **永久に送らない**（深夜着弾は無送信より悪い） |
   | 1時間前 | `[start−1h, start−300s]` | 遅れて届く。**上限を「開始」でなく「開始−5分」にして1時間前と5分前の同一tick連投を防ぐ** |
   | 5分前 | 現行のまま | 現行どおり |

   「前日20:00」は固定オフセットでなく JST カレンダー演算。**SQL は `session_start_at BETWEEN now AND now+28h+猶予` の粗い範囲で index scan し、正確な判定は JS 側**（インデックスを潰さないため）。
4. **バーストガードの軸は `created_at` ではなく「トリガー時刻 >= `REMINDER_V2_EPOCH`（コード内定数）」。**

日本は**ステマ規制＋景表法**。ローンチ前に事例が無いなら、**偽事例で埋めない**」。
同 §1 も FTC Consumer Review Rule（偽レビュー・偽体験談・2024-10-21 施行）を挙げる。
日本のステマ規制は「事業者の表示であることを隠して第三者の表示に見せかける」ことを禁じ、**サクラは典型例**。
設計正本 funnel-design も「コメント欄・疑似チャットは置かない（存在しない参加者を演出することになる）」と却下済み。

**疑似ライブ（録画をライブ形式で流す）とサクラは別物**。前者は開催形式の演出、後者は**他人の発言の捏造**。線はここ。

**代替の道はある**: 実在コメントを他の視聴者に見せるなら捏造ではなく、却下理由（存在しない参加者）が消える。
**週5回20時固定にしたことで1回あたりの密度が7倍になった**ので条件は近づいた。
**ただし今は有効化しない** —— `特典請求` タグ保持者が 0人の段階で相互表示を入れると、
**コメントが流れない画面＝「誰もいない」が可視化されて逆効果**。1回あたり数人が同時視聴する状態になってから。
実装は `/state` が返すコメントに当該セッションの `webinar_user_comments` を混ぜるだけで小さい。

  **分かれ目は「表示している希少性が実在する事実に基づくか」の一点**。このウェビナーは毎日19〜23時に
