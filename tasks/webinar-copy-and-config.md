# ウェビナー導線の文言・設定値（本番投入用）

2026-08-27 決定。**コードではなく DB のデータ**なので、デプロイとは独立に投入できる。
本番への書き込みは Claude Code の classifier にブロックされるため、**ユーザーが curl を実行する**。

---

## 1. `intro_text`（セッション選択画面・タイトル直下）

```
Xで発信しているのに、
問い合わせも仕事も増えない。

その原因のほとんどは、投稿の書き方ではなく、
書く前に決めていないことのほうにあります。

このズレがどこで起きるのかを、
1本の動画（約57分）にまとめました。
```

### なぜこの長さ・この順序か
- **短くした理由**: 長文/短文の分かれ目は「①トラフィックの温度 ②価格帯 ③感情/理性軸 ④ブランドの年数」で、
  **4変数が決まれば長さは自動的に決まる**（writing 争点マップ §2-1「長文コピーと短文コピー、どちらが転換するか」）。
  この読者は**ウォーム**（LINE登録済み・特典受取済み・リンクを踏んだ）で**価格ゼロ**。長文が効く条件に1つも当たらない
- **「約57分」を見返りの後に置く**: 無料コンテンツで唯一残る反論は「時間」
  （第二の脳: "反論の4分類で洗い出してから潰す" [観察] / 16-objection-proof-cta）。
  隠すと信頼側の反論が立つので**書く。ただし位置を見返りの後に下げる**
- **「誰向けでないか」は書かない**: LINE 本文側に「投稿のテクニックの話ではありません」が入るので重複する
- **「なぜ4項目を聞くのか」もここには書かない**: フォームの `description` 側に置く（役割を分ける）

## 2. 事前申し込みフォーム（新規作成）

`POST /api/forms` で作成し、その id を `webinars.pre_registration_form_id` に設定する。

- **name**: `ウェビナー 事前申し込み`
- **description**（管理用メモ。利用者には出さない）:
  `セッション選択画面で回を選んだときに開く。送信をもって視聴予約が確定する。月商は funnel-design §5 で一度却下された項目だが、2026-08-27 にユーザー判断で「選択式レンジ＋用途説明」の形で復活させた（自由記述にはしない）。`

### fields（JSON）
```json
[
  {
    "name": "x_purpose",
    "label": "Xを運用している目的に、一番近いものはどれですか？",
    "type": "radio",
    "required": true,
    "options": ["仕事や売上につなげたい", "認知を広げたい", "採用・仲間集め", "まだ決まっていない"]
  },
  {
    "name": "business",
    "label": "いま何をやっていて、何を売っていますか？（1〜2行で大丈夫です）",
    "type": "textarea",
    "required": true
  },
  {
    "name": "monthly_revenue",
    "label": "現在の月商はどのあたりですか？（だいたいで大丈夫です）",
    "type": "radio",
    "required": true,
    "options": ["これから", "〜10万円", "10〜50万円", "50〜100万円", "100〜300万円", "300万円以上"],
    "help": "個別相談でご提案の前提にします。金額そのものを話題にすることはありません。"
  },
  {
    "name": "bonus_impression",
    "label": "特典を受け取ってみて、いま感じていることを教えてください",
    "type": "textarea",
    "required": true
  }
]
```

**`help` を出す実装が無ければ、`label` の末尾に改行して同じ文を入れる。** 用途説明は落とさないこと。

### 項目設計の根拠
- **月商を選択式レンジにした理由**: 設計正本 `auto-webinar-funnel-design.html` §5 は月商を名指しで却下していた
  （「先に聞くと**相談が値踏みの場になる**」「**最も離脱を生む項目**」）。2026-08-27 にユーザー判断で復活させたが、
  自由記述のままだと却下理由がそのまま効くので、**1タップで済むレンジ＋用途説明**にして入力負荷と値踏み感の両方を下げた
  （uxw 正本 D-62「電話番号の用途説明」[経験則]／D-63「任意化の事例限界」[経験則]。
  **D-63 の効果量は単一事例・n数不明なので一般化しない**）
- **必須マークを個別に付けない**: 4項目すべて必須なので、シート上部に `すべての項目にご回答ください。` と1行置く方式に統一する
  （uxw 争点 required-optional-marking「現時点の実務解」＝必須が多数派なら GOV.UK 方式。**方式をフォーム内で混在させないことが最重要**）
- **「特典の感想」のラベル**: 「読んだ感想」にしない。特典と案内が同時に届くので、**まだ読んでいない人が答えられなくなる**。
  「受け取ってみて、いま感じていること」なら未読でも答えられる
- **プレースホルダーをラベル代わりに使わない**（uxw 争点 placeholder-as-label・ほぼ決着）

## 4. 特典の応答メッセージを2バブルに分ける

対象 auto_reply: `d8f05c9e-5e2c-4a1a-b8c9-2df1b6b18177`（keyword `特典` / exact）

**課金は増えない。** 応答メッセージ（Reply API）は課金対象外 `[公式]` で、吹き出しは1配信3つまで `[公式]`。
翌日にシナリオで送る案は**案内が課金1通×全員分**乗るうえ、「申し込みたいと思った瞬間が熱量の最高潮」`[観察]`
（`2026-0803-the-five-stage-consult-funnel`）を捨てることになるので採らない。

### バブル2（ウェビナー案内）
```
特典を受け取った方にだけ、動画を1本ご案内しています。

問い合わせも仕事も増えない。

　投稿を書く前に考えておきたい5つのこと」（約57分）

https://ai-komon.nobel824.workers.dev/t/qFMW0SK
```

**冒頭の `──────────` は削る**（バブルが分かれるので区切り線が不要になる）。

### 文言変更の根拠（前セッションの writing-consult / line-step-consult より）
- **「特別なウェビナーに招待します」は使わない。** 「特別」の実体が無い（毎日19〜23時に常時開催・特典を受け取れば誰でも見られる）。
  希少性の表示は**実在する事実に基づくかの一点**で決まる（writing 争点 §3-1）。
  加えて LINE 規約の禁止の型〈謳い文句〉＋〈セミナー開催等へ誘導〉の**誘導側を濃く塗る文**になる `[公式]`
  （`2026-0803-guideline-bans-the-pitch-not-the-business`）
- **代わりに使える実在の事実**: このリンクは特典返信と翌日フォローにしか入れていないので、
  **「特典を受け取った方にだけ、動画を1本ご案内しています。」は事実**
- **本文で「ウェビナー」という語を使わず「動画」のままにする**
- **痛みを先に立てる**（"予防ではなく治療を売る" [観察] / 04-reader-intent。Sugarman の経験則で学術データではない）
- **「あわせて、」を削った理由**: 特典と動画を並列に置く語で CTA が2本立つ
  （"1通1メッセージ・単一CTAの原則" [観察] / 08-media-specific。「可能な限り」の実務観察で実験データは無い）。
  バブルを分けたので並列の問題自体が構造で解ける
- **足さないもの**: 「見れば伸びる」系の成果の約束（規約の両翼が揃う）

## 5. `auto_reply` の複数バブル対応（実装が要る・未着手）

**リポジトリ内に複数メッセージ送信の前例が1つも無い**（`replyMessage` / `pushMessage` の全12箇所が単一要素の配列）。
`auto-reply.ts:140` が `buildMessage` を1回だけ呼んで `[replyMsg]` を渡している。

### 設計（additive・後方互換）
`packages/db/migrations/074_auto_reply_second_message.sql`:
```sql
ALTER TABLE auto_replies ADD COLUMN response_type_2 TEXT;
ALTER TABLE auto_replies ADD COLUMN response_content_2 TEXT;
```

- **両方 NULL なら従来どおり1通**。既存の全 auto_reply は挙動不変
- `response_content_2` があれば `buildMessage` をもう一度呼んで `[msg1, msg2]` を渡す
- ログ（`logOutgoingMessage`）は**2通分記録する**。片方だけだと配信実績が実態とずれる
- 3通目は作らない（LINE の上限は3だが、YAGNI。必要になったら JSON 配列に移行する）

### 却下した案
- **`response_content` を JSON 配列としても解釈する**: migration 不要だが、`[` で始まる**本文**（「[重要] …」等）と
  区別できず誤爆する。text 本文が `[` で始まるのは普通にあり得るので採れない
- **区切り文字で分割**: 本文に区切り文字が現れたときに誤爆する

### 危険 zone の注意
`auto_reply` は**この worker の全アカウント（AI顧問／クラファン／サガリ藤）が共有する経路**。
「NULL なら従来どおり」が壊れると全アカウントの応答が壊れるので、**既存 auto_reply の挙動が変わらないテストを必ず書く**。

## フォームの説明欄（`forms.description`）は視聴者に表示される — 2026-09-06 に判明

**`forms.description` は内部メモ欄ではなく、ユーザーに見える表示欄。** 3面のうち2面で描画される。

| 面 | 描画 |
|---|---|
| ウェビナー視聴中のCTAフォームシート | `main.tsx` の form phase で**無条件に表示** |
| LIFF単体フォームページ | `form.ts` で `!hasSubmitWebhook` のときだけ表示 |
| ウェビナー事前申し込みシート | 描画していない（`PreRegistrationSheet` は自前の見出し・説明を持つ） |

管理画面の入力欄のプレースホルダーが「管理画面用のメモ(任意)」だったため、**設計メモがそのまま
本番で視聴者に見えていた**（発見時点で「無料相談 事前ヒアリング」「ウェビナー 事前申し込み」の2件）。
プレースホルダーは実態に合わせて直した。**フォームの設計意図はこのファイルに書く。DBの説明欄に書かない。**

### 退避した内部メモ（DBから削除したもの）

**無料相談 事前ヒアリング（`95a1355f-8f5d-4ffb-b0a0-4900c13bc6ee`）**
> オートウェビナー視聴中のCTAから開く。聞くのは2項目だけ（funnel-design §5）。投資可能額・フォロワー数・投稿頻度・自走/伴走希望は聞かない。2026-08-27: 事業内容と月商は事前申し込みフォームで取得するため business を削除。アカウントは URL だとブラウザを離れる必要があり障壁が高いので ID に変更した。

**ウェビナー 事前申し込み（`e392a03b-1180-40c9-bae3-a545e8cdb190`）**
> セッション選択画面で回を選んだときに開く。送信をもって視聴予約が確定する。月商は funnel-design §5 で一度却下された項目（値踏みの場になる・最も離脱を生む）だが、2026-08-27 にユーザー判断で「選択式レンジ＋用途説明」の形で復活させた。自由記述にはしない。
