# 友だち追加アンケート 再設計（デモグラ版）

- **日付**: 2026-07-16
- **対象**: 友だち追加後の最初の挨拶（グリーティング）で出すアンケートフォーム
- **ステータス**: 設計確定（実装計画待ち）

## 背景・課題

現行のアンケートは **副業を前提**にした設問構成になっており、選択肢も1つしか選べない。
運用側が本当に知りたいのは「どんな読者が集まっているのか（属性）」であり、それを踏まえて
**今後どんな商品を作る／紹介するか**を判断したい。

そのための第一歩として、まずは軽量なデモグラフィック調査に作り替える。

## ゴール / 非ゴール

**ゴール**
- 副業前提の設問を撤去し、立場・年齢・性別だけを軽く取得する
- 全問「タップ1回」で終わる単一選択にし、30秒で完了できる回答体験にする
- 誰が集まっているか（属性分布）を後から集計できる形で保存する

**非ゴール（今回やらない）**
- 「何を望んでいるか（関心・ニーズ）」設問の搭載 … 今回は見送り（デモグラに絞る）
  → **後日撤回**: リリース後に Q4（自由記述・任意）として追加された（後述）
- 順位付け（1位/2位/3位）設問タイプの新規開発 … 不要（全問単一選択のため）
- 支払い意欲・予算感の設問 … 聞かない
- 選択肢別の自動集計 UI … 今回のスコープ外（別途）

## 重要な発見：アンケートはコードに存在しない

調査の結果、このアンケート（設問・選択肢）は **コードにもシードにも存在せず、稼働中インスタンスの
DB に「データ」としてのみ存在する**ことが判明した（`POST /api/forms` で実行時に作られる）。

- admin(apps/web) には **フォームを作成・編集する UI が無い**（あるのは回答閲覧 `form-submissions` のみ）。
  設問を変える正規ルートは REST API（`POST/PUT /api/forms`）の直叩きだけ。
- グリーティングとの紐付けも `?form=FORM_ID` という**データ**（エントリールート／シナリオのメッセージ）
  に埋まっており、コードではない。

→ 「コードを直して設問を変える」対象が存在しないため、"設問の削除・追加・調整を今後も気軽にやりたい"
という要望に応えるには、**admin にフォーム編集 UI を新設する**のが本命。これを今回の実装スコープとする。

## 実装スコープ：admin フォーム編集 UI（確定）

apps/web(Next.js) に **フォーム管理ページ（`/forms`）** を新設し、既存の `GET/POST/PUT/DELETE /api/forms`
に接続する。これにより、今回の3問デモグラアンケートも、今後の設問の削除・追加・調整も、UI から行える。

**このページで最低限できること**
- フォーム一覧（名前・回答数・有効/無効）を表示
- 新規フォーム作成／既存フォーム編集（フォーム名・説明・`is_active`・送信後設定）
- **設問(fields)の編集**：設問の追加・削除・並べ替え、各設問の label／type（text/textarea/select/radio/checkbox/number/tel/email/date）／required／options（選択肢の追加・削除）
- 削除
- 既存の `form-submissions`（回答閲覧）とサイドバーで並べる

**このUIで今回のアンケートを作る手順**（B案：新フォーム作成）
1. `/forms` で新規フォームを作成し、Q1 立場／Q2 年齢層／Q3 性別 の3設問（全て radio・必須）を入力して保存 → 新 `formId` を得る
2. グリーティング（friend_add シナリオ／エントリールートの intro メッセージ）の LIFF URL の
   `form` パラメータを新 `formId` に差し替える（既存のシナリオ/エントリールート編集画面で行う）
3. 旧フォームは非アクティブ化（`is_active=0`）または温存（要判断）

**デプロイ経路**：フォークの main へ merge → GitHub Actions（[[line-harness-deploy-path]]）。merge 後に
稼働中 admin で上記手順を実施する。

## データ保存・集計

- 回答は `form_submissions.data`（JSON）に保存。`save_to_metadata=1` なら `friends.metadata` にもマージ。
- 全問単一選択なので、各回答は単一文字列。マイグレーション不要。
- 選択肢別の集計は現状 UI 未実装（`form-submissions` は個票閲覧のみ）。今回は生データが貯まればよしとし、
  集計の可視化は別スコープ。

## 検証（Verification）

- LIFF フォームを実機（または LIFF ブラウザ）で開き、Q1〜Q3 が単一選択で表示され、未選択時に required
  バリデーションが効くことを確認する
- テスト送信を1件行い、`form_submissions.data` に `role`/`age_range`/`gender`/`wanted_info` が
  期待どおり保存され、お礼メッセージ送信とタグ付与が発火することを確認する
- グリーティング経由で新フォームが開く（LIFF URL の formId が新IDに向いている）ことを確認する

## 実装スコープの非ゴール（フォーム編集 UI 側）

- ランキング（1位/2位/3位）設問タイプの新規実装 … しない（既存の型のみ対応）
- 選択肢別/設問別の集計・可視化 … しない（回答閲覧は既存 `form-submissions` のまま）
- 設問の条件分岐・複数ページ設定などの高度な編集 … しない（既存 fields の素直な CRUD のみ）
- ~~送信後設定（tag/scenario/message/webhook）の編集UI~~ … **撤回（下記参照）**

### 非ゴールの撤回：送信後設定の編集UI（2026-07-17）

当初は「送信後設定は編集UI不要」と割り切ったが、**これは誤りだった**。稼働中の旧フォームには
`onSubmitTagId`（回答者へ「アンケート回答済み」タグ付与）と `onSubmitMessageContent`（回答後のお礼
メッセージ）が設定されており、**これらこそ運用の要**だった。新フォームに切り替えるには同等の設定が要るが
UI が無く、生 API を叩くのは「UI で管理できるようにする」という本設計の趣旨に反する。
→ タグ／メッセージ（なし・テキスト・Flex）の編集UIを追加した（PR #13）。
`onSubmitScenarioId` / webhook 系は引き続き非ゴール（body に含めず部分更新で保全）。

## 積み残し（別課題）

- `PUT/DELETE /api/forms/:id` が**認証なしで通る**（公開パスの正規表現が HTTP メソッドを見ておらず、
  LIFF 向けに GET を公開する意図が書き込み系まで漏れている）。実データを書き換えられるため要修正。
- フォーム編集UIの自動テストが無い（null クリア・Flex 非破壊は回帰リスクが高い）。
- 属性別の集計UI（例: 事業者が何%か）は未実装。回答が貯まってから検討。
